## OIDC 登录流程方案讨论（只读 + 概念澄清）
- 理清 Shopify 第一趟 authorize 的职责：校验参数后把浏览器送到登录页（不发 code），用户未认证时 IdP 必须尝试认证。
- 三个参数（redirect_uri / state / nonce）都由 Shopify 生成，IdP 只保管 + 归还：state 在发 code 的 302 原样回传；nonce 写进 ID Token 的 claim；redirect_uri 是 302 目标本身且 token 阶段再校验。
- state 是 CSRF 对账凭证（不是流程状态机），Shopify 自留副本比对；对 Shopify 只有一次 authorize，用户说的两趟是 IdP 内部视角。
- 暂存方案对比：加密 URL 塞 state（mmos 做法，实测 378→884 字符）vs Redis 短 key。mmos 用加密串的原因是登录系统要自己 decrypt 还原回跳 URL，且加密 state 是全局约定；Redis 那段 SETNX 只是去重，不存参数。结论：本项目用 Redis 短 key 合理。
- 纠正自己多处误判：mmos 登录与 authorize 在同一 repo/同一 Laravel 应用（不是不同系统）；ShopRedisFacade 只是那 12 处 Hash/原子命令用法，60+ 处业务缓存走 ShopCacheFacade（Cache 抽象无 hset/expire/ttl）。

## 登录流程设计要点（方案）
- 用户方案：uuid 作 rid → Redis 存 Shopify URL → 前端登录带回 rid → 返回 redirect_url 带 rid+JWT → authorize 取缓存验登录态发 code。
- 补的安全点：rid 与 uid 必须绑定（登录接口把 uid 写进 Redis 记录），否则可拿他人 rid + 自己 JWT 串号；用 getDel 原子取删防重放；JWT 建议含 rid claim。
- 时序纠正：第一趟 authorize 无 uid 是正常的，uid 在登录接口验证密码后才写入缓存。
- 命名：rid（前端可见）vs Shopify state（藏在缓存里，最后原样回传），别混。
