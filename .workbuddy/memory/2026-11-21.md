## OIDC 异常体系规划与落地
- 用户指出 CommonException 用在 OIDC 上响应形态不对：authorize 错误是 302 重定向附 error/state，token 错误是 400 JSON `{"error":...}` + `Cache-Control: no-store`，而 CommonException/Handler.php:35-41 统一输出 `code/message/data` 信封。
- 设计上收敛为：**OIDC 协议 error 码是预期结果（正常业务流程），由 business 直接 return 响应，不走异常**；异常类只处理真正的意外（server_error / temporarily_unavailable）。用户明确否定拆 `AuthorizationException`/`TokenException` 两个子类，要单一类传错误码。
- 参考 `old-six-php/app/Exceptions/SerpApiException.php` 风格（extends RuntimeException + 类常量错误码 + readonly 属性 + 详细分类注释）。
- 新增 `app/Exceptions/OidcException.php`：仅两个常量 `SERVER_ERROR='server_error'` / `TEMPORARILY_UNAVAILABLE='temporarily_unavailable'`，构造参数 `errorCode`(readonly string) / `message` / `httpStatus`(readonly ?int)。`php -l` 与 autoload、常量读写均已验证。
- **未改** Handler.php / CommonException.php（工作区原有的 M 状态是用户自己的改动）。OidcResponse 响应构造器、Handler 分支、OidcErrorCode enum 仍在规划中，未落地。

## 追加（14:30）异常自渲染（参考 mmos-membership-marketing）
- 那边 `OAuthServerException` 自带 `render()`，Handler 用 `if (method_exists($e, "render")) return $e->render();` 统一委托——不用给每个异常写 instanceof 分支。其 Enums/Exceptions 成对（各 28 个）。那边字段名是 `error_type`、业务错误 status 常用 200，这两点**不能照抄**（OIDC 要 `error`、token 错误必须 400）。
- `OidcException::render()`：`redirectUri` 有值 → 302 附 `error` + `error_description` + `state`（原样回传）；否则 → JSON `{"error","error_description"}` + `httpStatus`(默认400) + `Cache-Control: no-store`。`message` 只进日志不外泄。
- `Handler::render()` 在两个 instanceof 分支后、parent 兜底前加 `method_exists` 委托钩子（那边的模式）。
- 实测经 Handler 委托：REDIRECT 302 location 带三参数且 state 原样；JSON 400 + no-store + 标准 body；SERVER 500 不泄漏内部 message。
